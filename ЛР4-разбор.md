## Что от нас требуется простыми словами

Раньше Express принимал HTTP-запросы и работал с PostgreSQL. Теперь делаем
страницу в браузере на React. На ней пользователь меняет список публикаций,
а страница сразу показывает результат. ЛР4 автономна: запросы к нашему API,
пароли и Supabase для неё не нужны. Vite запускает сервер разработки,
который отдаёт клиентские файлы. Это не сервер хранения публикаций.

Нужно показать три вещи. Во-первых, состояние: React помнит коллекцию и
введённый текст. Во-вторых, эффекты: коллекция читается из браузерного
хранилища и сохраняется при изменении. В-третьих, интерфейс: добавление,
редактирование, удаление, фильтрация и сортировка работают без перезагрузки.

## Минимум теории

**Компонент** — функция, возвращающая описание части страницы. `App` описывает
общую страницу, `PostForm` — форму, `PostCard` — карточку. Имя компонента
начинается с большой буквы, иначе JSX воспримет его как обычный HTML-тег.

**JSX** — запись разметки внутри JavaScript. Это не строка HTML. Vite с
плагином React преобразует её в JavaScript. В фигурных скобках внутри JSX
пишутся выражения: `{post.title}` выводит заголовок. `className` задаёт
CSS-класс, `htmlFor` связывает подпись с полем.

**Состояние** — память конкретного экземпляра компонента между рендерами.
`const [search, setSearch] = useState('')` создаёт текущее значение и функцию
обновления. Обычная переменная не сохраняет изменения таким способом и её
присваивание не сообщает React, что интерфейс нужно обновить.

**Рендер** — вызов компонентов для вычисления нового описания интерфейса.
Затем React вносит необходимые изменения в DOM — структуру страницы браузера.
Вызов `setPosts` не меняет переменную `posts` в уже выполняющемся обработчике.
Он ставит обновление в очередь. Следующий рендер получит новое значение.
Несколько обновлений в одном обработчике React обычно объединяет.

**Функциональное обновление** нужно, когда новое значение зависит от старого:
`setPosts(previous => [...previous, post])`. React передаёт актуальное
предыдущее значение в нашу функцию. Функция возвращает новое состояние.
Имя `previous` придумали мы, оно не является ключевым словом JavaScript.

**Неизменяемое обновление**: исходный массив не меняем через `push`/`splice`.
Для добавления создаём новый массив через spread, для замены используем `map`,
для удаления — `filter`. Объекты тоже копируем через `{ ...post, ...values }`.
React сравнивает ссылки, поэтому создание нового массива здесь существенно.

**Props** — входные параметры компонента. Родитель передаёт в `PostForm`
объект формы и функции действий. Форма не создаёт вторую копию коллекции.
Она вызывает переданную функцию, а источник данных остаётся у родителя.

**Хук** — специальная функция React или наша функция, использующая хуки.
Хуки вызываются в одном порядке на верхнем уровне компонента/другого хука.
Их нельзя переносить внутрь `if`, цикла или обработчика нажатия.

**Побочный эффект** — взаимодействие с чем-то вне вычисления разметки.
Здесь это чтение/запись localStorage и изменение `document.title`.
`useEffect(callback, [])` запускает настройку после монтирования.
`useEffect(callback, [posts])` повторяет её, когда изменилась ссылка `posts`.
Без массива зависимостей эффект выполняется после каждого коммита компонента.
Зависимости сравниваются через `Object.is`.

**Cleanup** — функция, которую эффект возвращает. React вызывает её перед
следующей настройкой эффекта с изменившимися зависимостями и при удалении
компонента. Мы отменяем таймер и снимаем обработчик события.

**StrictMode** в разработке дополнительно проверяет код: повторяет рендер и
цикл setup → cleanup → setup эффектов. Это помогает заметить пропущенную
очистку. Поэтому не стоит говорить, что эффект с `[]` «всегда запускается
ровно один раз». В обычной производственной работе он запускается при
монтировании, а при новом монтировании — снова.

**localStorage** хранит строки для конкретного origin: протокол, хост, порт.
Чтобы сохранить массив, используем `JSON.stringify`, чтобы восстановить —
`JSON.parse`. Сохранение не является серверной записью и не синхронизирует
публикации между компьютерами. `sessionStorage` дополнительно отделён по
вкладке и обычно существует до окончания её сеанса.

**Debounce** — перенос действия до окончания серии быстрых изменений.
Каждая правка запускает таймер на 500 мс. Следующая правка отменяет старый
таймер и запускает новый. Сохраняется последняя версия коллекции.
Изменение незавершённой формы в нашей реализации не сохраняет черновик.
Эффект реагирует на добавление, удаление и подтверждённое редактирование.

## Где начали писать и как двигались дальше

1. Создали отдельную папку `client`, подготовили Vite, React и React DOM.
   HTML-точка входа — `client/index.html`, JavaScript-точка — `src/main.jsx`.

4. В `PostList.jsx` связали состояние, CRUD, поиск, сортировку и эффекты.
5. В `PostForm.jsx` и `PostCard.jsx` вынесли повторяемую разметку.
6. В `App.jsx` собрали страницу, в `styles.css` оформили её.
7. Добавили проверки хранилища, выполнили сборку и проверили интерфейс.

Это порядок реализации. При открытии страницы порядок исполнения другой:
`index.html → main.jsx → App → PostList → useLocalStorage → PostForm/PostCard`.
После того как React применит разметку, выполняются эффекты.

## Оставшиеся файлы

`index.html`: язык ru, кодировка UTF-8, настройка масштаба мобильной страницы,
начальный title, div#root и подключение main.jsx как ES-модуля. Здесь нет списка
публикаций: React построит его внутри root.

`vite.config.js`: defineConfig описывает настройки сборщика, react() подключает
обработку React/JSX. export default отдаёт конфигурацию Vite.

`package.json`: type=module разрешает import/export внутри клиента. dev запускает
Vite, build создаёт dist, preview показывает dist, test запускает Vitest в jsdom.
react выполняет модель компонентов, react-dom связывает её с браузерным DOM.
Vite и его React-плагин нужны для разработки/сборки, Vitest/jsdom/Testing Library —
для проверок. package-lock.json создаёт npm и фиксирует установленные версии.
node_modules и dist в Git не попадают. Секретов у клиента нет.

`styles.css`: :root задаёт шрифт/цвета, * включает border-box. site-header
закрепляет шапку через sticky. intro и summary оформляют название/счётчик.
workspace использует Grid для формы и списка. label/input/textarea/select
оформляют поля, form-actions — кнопки. filters задаёт сетку поиска и select.
post-card/card-top/card-bottom оформляют карточку. overflow-wrap:anywhere
переносит длинные непрерывные строки, white-space:pre-wrap сохраняет переносы
описания. notice/error — сообщения, empty-state — пустой список. Три @media
адаптируют отступы и сетку под 1260, 900 и 650 пикселей. CSS не хранит состояние
и не сохраняет публикации. Значения цветов и размеров являются оформлением.

`useLocalStorage.test.jsx`: beforeEach очищает отдельное тестовое хранилище jsdom
и включает управляемые часы. afterEach размонтирует хуки, восстанавливает функции
и обычные часы. renderHook запускает настоящий React-хук. act отмечает действия,
после которых React должен применить обновления. expect проверяет результат.
vi.advanceTimersByTime двигает тестовое время без ожидания полсекунды в реальности.
vi.spyOn наблюдает вызовы или имитирует отказ хранилища. Три значения в it.each
создают три отдельных проверки повреждённых данных. Всего получилось 11 тестов.
Эти подмены существуют только в тестах и не используются приложением.

## Полный путь одного добавления

1. Пользователь вводит заголовок. onChange вызывает changeField.
2. changeField вызывает setForm. React перерисовывает форму с новым value.
3. Пользователь отправляет форму. Вызывается handleSubmit.
4. preventDefault отменяет обычную навигацию. trim и ограничения проверяют ввод.
5. Создаётся объект с id/createdAt, setPosts возвращает новый массив.
6. React показывает ещё одну карточку и обновляет счётчики.
7. Эффект document.title меняет заголовок вкладки, если изменилось количество.
8. Эффект хранилища отменяет старый таймер и планирует запись новой коллекции.
9. Через 500 мс JSON.stringify превращает массив в строку, setItem сохраняет её.
10. После F5 эффект начального чтения восстановит массив через JSON.parse.

При редактировании шаг 5 использует map и сохраняет id/createdAt.
При удалении используется filter. Поиск и сортировка не меняют posts,
поэтому сами по себе не запускают сохранение коллекции.

## Как показывать преподавателю

```powershell
git switch 24
cd client
npm ci
npm run dev
```

Открыть http://localhost:5173/ или точный адрес Vite. Показать начальные записи,
добавить свою, отредактировать её, найти по части названия/игры, выбрать тип,
изменить порядок. Вернуть все материалы, удалить тестовую запись.
После каждого изменения дождаться «Сохранено в браузере» и нажать F5.
Редактирование/удаление должно сохраниться. Фильтры и форма после F5 сбрасываются,
потому что сохраняется только массив публикаций.

В DevTools открыть Application → Local Storage → нужный адрес →
game-media-posts-v1. Показать JSON-массив. localhost и 127.0.0.1 — разные хосты,
порт 4173 и порт 5173 тоже дают разные хранилища. Это объясняет ситуацию,
когда на другом адресе снова видны примеры.

Проверки из папки client: npm test — 11 тестов, npm run build — сборка.
Пустую форму остановит required, пробельную — trim, слишком длинную строку —
maxLength и проверка обработчика. Эти ограничения обеспечивают разумный размер
локальной коллекции, они не являются сетевой защитой от DDoS.

## Что могут спросить дополнительно

**Почему не useEffect для поиска?** Это вычисление из уже имеющихся данных.
Отдельное состояние результата и эффект создавали бы лишнюю синхронизацию.

**Почему sort безопасен, хотя он меняет массив?** Мы сортируем новый массив,
возвращённый filter. Исходный posts остаётся прежним.

**Почему loaded нужен?** Первый рендер содержит posts=[]. Эффект загрузки
запросит изменение posts, но эффект сохранения этого же рендера всё ещё видит
старый снимок. loaded=false запрещает ему записывать пустой список.

**Почему при ошибке чтения не сохраняем примеры?** Чтобы не затереть исходную
строку, которую пользователь ещё может восстановить. Работать в памяти можно,
но это явно показано предупреждением. Для восстановления сначала сохранить
копию строки в DevTools, затем исправить/удалить наш ключ и обновить страницу.

**Что делает cleanup?** Отменяет старую отложенную запись и снимает старый
обработчик pagehide. Без этого накопились бы действия с устаревшими коллекциями.

**Почему не Redux?** В этой работе состояние небольшое и используется внутри
одного раздела. useState и props покрывают требования задания.

**Как сделать ленивое чтение useState?** Передать функцию-инициализатор,
например useState(() => readStoredPosts()). Она должна обработать отсутствие
ключа и ошибки, не записывать данные. В нашей реализации чтение сделано эффектом
с [], поскольку это явно требуется в условии. Это другой вариант, а не второй
параллельный способ чтения в работающем приложении.

**Как имитировать серверную загрузку?** В эффекте [] создать таймер setTimeout,
в нём вызвать setPosts и убрать индикатор загрузки. Вернуть clearTimeout.
В нашем приложении искусственной секундной задержки нет: выбраны другие
дополнительные эффекты — автосохранение и document.title.

**Что с большой коллекцией?** Сейчас есть предел 500. При дальнейшем росте можно
профилировать список, мемоизировать дорогую фильтрацию через useMemo и применять
виртуализацию. React.memo полезен при стабильных props, но не заменяет измерения.

**Что не гарантирует localStorage?** Синхронизацию устройств, резервную копию,
сохранность после очистки данных браузера и передачу публикаций другим
пользователям. При аварийном закрытии до автосохранения последняя правка может
потеряться. Одновременное редактирование в нескольких вкладках не согласовывается.
Это ограничения автономной ЛР4. Подключение REST API предусмотрено в ЛР5.
